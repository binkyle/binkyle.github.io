多核同步机制：Spinlock、Barrier 与原子操作的设计边界

Bin2026/10/19嵌入式系统与 AUTOSARAUTOSAR多核并发编程RTOS大约 21 分钟

Core0 每 10 ms 更新一帧传感器数据，Core1 每 20 ms 读取一次。刚好在 Core1 读取到一半时，Core0 又开始写入：时间戳已经变了，数据数组却仍属于上一帧。程序并不会立刻崩溃，但控制算法拿到的是不一致的快照。

再换一种场景：三个 Core 分别初始化通信、数据和控制模块。Core0 两毫秒就完成，而 Core2 要八毫秒。所有 Core 都完成初始化之后才能开放后续功能，单靠保护共享数据的 Spinlock 还不够。

这两个例子分别对应临界区互斥与阶段会合。前者常用 Spinlock，后者可以用 Barrier 组织；二者都建立在正确的原子操作、内存访问顺序和调度前提之上。我们从 AURIX TC3xx 的底层能力出发，再看 AUTOSAR OS 能提供哪些同步服务。

1. 多核同步的四个基本问题

在一个双核 ECU 上，Core0 更新传感器采样结果，Core1 根据最新结果执行计算。假设共享数据包含时间戳、状态和一组测量值。即使单个字段的访问足够短，读取者也可能在写入尚未完成时获得新旧混合的数据。

一个正确的通信方案需要分别回答四个问题：

维度关注内容设计对象
原子性（Atomicity）某次操作是否被并发执行者观察为不可分割单个读改写或规定大小的访问
互斥（Mutual Exclusion）是否同一时刻只有一个执行者进入临界区共享缓冲、设备寄存器、复合状态
可见性与顺序（Visibility / Ordering）先写数据再发布状态，其他核能否按协议观察原子变量、内存同步、发布协议
进度（Progress）等待者能否最终获得锁、事件或阶段放行调度条件、参与者、超时与恢复

几个概念并非互相替代。拥有原子读写操作，并不会自动使一组多字段更新原子化；一把正确的锁也不会自动保证所有参与者完成初始化后一起进入下一阶段。

2. 原子操作：构建同步协议的底层能力

2.1 普通读写与读改写操作

考虑一个表示资源占用状态的共享标志。若获取过程是先读取“空闲”，再单独写入“已占用”，两个核可能都在写入前看到空闲。即使读取和写入各自是完整的，检查和占用组成的复合步骤并没有原子性。

硬件原子读改写（Read-Modify-Write，RMW）则把比较、交换或更新组合为有规定原子语义的访问。例如：

  • Exchange / Swap：交换某个共享字与新值。
  • Compare-and-Swap（CAS）：仅当当前值匹配预期时完成更新。
  • Fetch-and-Add：在获得旧值的同时原子累加计数（是否提供由平台决定）。
  • 原子位操作：用于更新共享状态标志或位图（具体原子性由指令与平台保证）。

AURIX TC3xx 的公开指令资料包括 SWAP.W、CMPSWAP.W、LDMST 等同步相关指令。选用指令时还必须检查地址区域、对齐、访问宽度与目标存储器的支持情况，不能简单认为普通 C 赋值具有相同语义。

2.2 一个原子变量能完成多少工作

单个原子变量适合表达锁状态、轮次计数、就绪标志或某个简单统计量。复合业务对象则可能包含多个字段：

字段类型示例需要的一致性
sequence递增序号数据版本关联
timestamp时间戳与同一批测量值匹配
values[]数据数组一致的整组快照
status状态位与数据有效性匹配

即使 sequence 的加一是原子的，也不能由此认为所有字段能够一次完成更新。针对整组快照，可以设计受保护缓冲、双缓冲、带序号的无锁协议或消息队列；这些方案都必须定义各字段如何发布、何时读取，以及出现重试或覆盖时如何处理。

3. Spinlock：对临界区建立互斥访问

Spinlock 是一种忙等待同步机制。获取者尝试将锁从可用状态切换为持有状态，失败时等待并重试，直到条件满足或返回规范定义的错误。

AUTOSAR OS 在多核场景中通过 GetSpinlock、TryToGetSpinlock 和 ReleaseSpinlock 等服务提供跨核互斥能力。具体可用性、错误检查和调用上下文由 OS 规范与项目配置决定。

图里先写后读只是其中一种执行顺序；若 Core1 先获得锁，写任务也必须遵守同一套互斥规则。

3.1 锁保护的是完整访问协议

在共享缓冲区的例子中，若写入者更新数据时持锁，而读取者从不获取同一把锁，锁就没有覆盖读写冲突。保护方案必须先明确所有访问者的读写方向，再约定哪些访问受同一个同步协议约束。

对于复合对象，临界区往往应该包含完整的一次快照读取或更新。只在复制前后分别加锁而在中间释放，未必能防止读写交错。

真正的临界区范围，要从数据一致性目标推导，而不是由 memcpy 的长度或一个 API 名称直接决定。

3.1.1 一个可运行思路的共享快照示例

沿用开头的采样场景，Core0 每 10 ms 更新一次 SampleFrame，Core1 每 20 ms 读取。帧由版本号、时间戳、测量值和质量位组成，实际项目中可以放在两个 Core 都能访问的共享 RAM 段里。

下面用标准 OS API 名称表示最重要的锁协议，Spinlock_Frame 和 g_frame 是这个示例自定义的配置对象名。这里没有加入业务错误码转换，只负责让加锁失败显式传给调用者。

typedef struct {
    uint32 sequence;
    uint32 timestamp_ms;
    sint32  sensor_value;
    uint8   quality;
} SampleFrame;

/* 由链接配置映射到两核可访问的共享区域。 */
extern SampleFrame g_frame;

StatusType PublishFrame(const SampleFrame *next)
{
    StatusType status = GetSpinlock(Spinlock_Frame);
    if (status != E_OK) {
        return status;
    }

    g_frame = *next;
    return ReleaseSpinlock(Spinlock_Frame);
}

StatusType ReadFrame(SampleFrame *snapshot)
{
    StatusType status = GetSpinlock(Spinlock_Frame);
    if (status != E_OK) {
        return status;
    }

    *snapshot = g_frame;
    return ReleaseSpinlock(Spinlock_Frame);
}

这个例子的关键不在于只有几行代码，而是两个方向的完整复制都发生在同一把锁的持有区间内。配置时必须确认该 Spinlock 允许两侧访问，函数从符合 OS 要求的任务上下文调用，共享内存具备正确的硬件访问属性。

还需要留意一点：GetSpinlock 成功之后如果出现提前返回，就可能让锁无法释放。因此，临界区代码应尽量短，释放路径要能明确审查。业务线程是否允许阻塞、允许持锁执行哪些 OS 服务，也必须遵守所选 Lock Method 的约束。

3.2 AUTOSAR Spinlock 的配置维度

AUTOSAR OS 定义了可选的 Spinlock Lock Method。它们影响持锁时本核的抢占与中断行为。

Lock Method占锁期间的附加保护工程取舍
LOCK_NOTHING不额外屏蔽本核中断或调度干扰较少，但需要额外确认本核执行者不会因抢占形成等待环
LOCK_WITH_RES_SCHEDULER采用调度器资源相关的保护方法减少持锁任务被本核任务抢占的风险，并带来调度约束
LOCK_CAT2_INTERRUPTS限制 Category 2 ISR 的抢占缩小中断相关的抢占窗口，增加相关中断延迟
LOCK_ALL_INTERRUPTS屏蔽相应范围的全部中断保护最强，但会显著影响中断响应预算

具体方法应根据共享对象访问者的上下文选择，尤其要核查持锁执行者是否可能被另一个也需要同一锁的执行者抢占。

AUTOSAR 还通过 Spinlock 访问许可和嵌套顺序配置限制非法使用。对于多把锁嵌套，必须设计统一的获取顺序；锁顺序不一致会形成循环等待。是否允许嵌套以及对应的错误行为，应以当前采用的 OS 规范及配置为准。

3.3 等待者和持有者对实时性的影响

当 Core B 在 Spinlock 上忙等待时，它会消耗本核处理时间。若 Core A 的持锁任务被高优先级执行者长期抢占，B 的等待时间会增加。

同步设计至少记录：

测量项定义对应关注点
Lock Wait请求获取到成功获得锁的时间竞争强度与持有者进度
Lock Hold成功获取到释放锁的时间临界区大小、抢占影响
访问耗时实际读取或修改共享数据的时间数据操作自身成本
业务端到端时延产生请求到结果被消费的时间调度、队列与锁的共同影响

这几项指标不同。一次调用耗时变长，可能是锁争用，也可能是持锁期间被抢占或任务调度延迟。

3.4 Spinlock 的错误处理

GetSpinlock 不是一个可以无条件忽略结果的“进入临界区”标记。OS 可能检查调用上下文、对象访问许可、嵌套顺序及重复获取等约束。

如果调用失败而后续代码仍访问本应保护的共享数据，可能破坏原先设定的互斥协议。准确的故障分析还需要看失败路径是否返回、是否调用 Hook，以及目标 OS 的保护配置，而不能单凭源码中的 (void)GetSpinlock(...) 认定存在实际故障。

4. Barrier：多个执行者的阶段会合

Barrier 的同步条件是：本轮指定的所有参与者都已到达，才能放行下一阶段。

例如，三个核分别准备传感器接口、共享状态和控制算法。只有三个初始化步骤均完成，依赖这些状态的处理流程才可以继续。

假设三个 Core 分别在第 2、5、8 ms 到达同步点，理想情况下 Core0 等待约 6 ms、Core1 等待约 3 ms，Core2 到达时便满足放行条件。放行意味着可以进入下一阶段，而不是三个 Core 在同一个时钟沿开始执行。

4.1 一次性 Barrier：计数与位图

若参与者固定为 N 个，且每个参与者恰好到达一次，一次性 Barrier 可以采用共享原子计数方式：参与者先完成本阶段工作，再通过原子更新记录自己的到达状态；达到 N 后，各参与者依据约定的发布与可见性规则离开等待。

另一种方法是使用原子位图。参与者拥有唯一标号，分别设置自己的到达位；待有效参与者对应的位全部设置，即满足会合条件。

这两种设计的共同基础是：并发更新不丢失、参与者不会重复计数、到达前的数据按协议正确发布。

一次性方案状态表达优势重要前提
原子计数已到达的参与者数量状态紧凑、实现直观每人准确计数一次
原子位图哪些参与者已经到达可定位缺席者参与者编号稳定、原子置位正确
每参与者独立状态分别记录各方进度减少竞争同一个更新位置状态可见性与比较协议正确

4.2 用 Spinlock 保护到达状态

Barrier 可以使用 Spinlock 来串行化计数更新，但等待其他参与者的阶段不能一直持有这把锁。

如果 Core0 更新完计数后继续持锁等待，而 Core1 必须获得同一把锁才能报告已到达，那么 Core1 永远无法推进会合条件。正确的协议会在完成必要的共享状态更新后释放互斥锁，再通过满足内存可见性要求的方式观察等待条件。

因此，Barrier 不一定依赖 Spinlock；有足够硬件支持时，原子更新同样可以构建会合协议。

5. 可复用 Barrier：轮次、放行和状态复位

一次性 Barrier 只描述一个阶段；周期性控制算法往往要在每一轮计算之后再次会合。复用时必须保证前一轮的状态不会被误认为新一轮的到达状态。

5.1 轮次信息不可缺少

可以观察两名参与者的时间关系：

时刻参与者 A参与者 B同步协议必须保证
第 1 轮末到达第 1 轮到达第 1 轮第 1 轮可以放行
进入下一轮已开始第 2 轮工作尚在退出第 1 轮不把上一轮状态当成新到达
第 2 轮会合等待 B 到达完成第 2 轮工作等待本轮参与者全部到达
第 2 轮结束继续执行继续执行可为下一轮复用同步状态

简单地保留一个“到齐”标志，会使后续轮次可能直接通过；在尚有参与者读取旧状态时直接清零，又可能引入新的竞态。

通用算法通常把到达状态与轮次标识（Generation）或相位翻转（Sense-Reversing）结合使用。实现需要协调到达、最后一个参与者触发放行、等待者读取状态，以及下一轮重新开始。

5.2 Counter 回绕与参与者缺席

有限宽度计数器最终会回绕。如果算法通过模运算比较进度，就必须明确何种轮次差下比较关系有效，并证明参与者不会越过允许的差距。动态加入、退出和故障重启会改变这一前提。

更常见的故障情形是某个参与者没有到达同步点。若 Barrier 采用忙等待且没有超时或缺席处理机制，其它参与者可能长期等待。是否由 Watchdog 检测并恢复，应由完整的看门狗服务路径和系统配置证明，不能把“有 Watchdog”当作 Barrier 算法正确性的替代条件。

6. Memory Barrier 与共享内存可见性

内存屏障（Memory Barrier）和阶段会合（Barrier Synchronization）名称相近，却解决不同层面的问题。

阶段 Barrier 约束多个执行者何时可以继续；Memory Barrier 约束 CPU 或编译器处理内存访问时的顺序与可观察性。一个正确的跨核同步协议往往同时需要状态同步和内存可见性保证。

6.1 volatile 与 NonCached 的边界

  • volatile 影响编译器对相应对象访问的优化处理，不提供一般意义上的跨核互斥协议。
  • NonCached RAM 可以减少与缓存相关的不一致条件，但一组独立读写仍可能被另一核在中途观察。
  • 原子操作提供规定宽度及操作类型的原子语义；是否同时提供所需的获取/释放顺序，要查目标平台和语言模型。
  • 内存同步指令与相关编译器约束用于建立所需的先后关系，但不会把多字段复制变成一个整体的原子事务。

因此，互斥、原子性和内存顺序应当分别设计，再共同验证。

6.2 数据发布协议

对于 Core0 生产、Core1 消费的数据，可以把同步过程拆成三个阶段：

  1. 准备数据：生产者在约定的共享区域完成写入。
  2. 发布可见状态：通过具备正确内存序的同步操作发布“数据已就绪”。
  3. 消费数据：消费者在确认就绪后，按协议读取完整数据或一致快照。

若数据会被下一次写入覆盖，还需定义读写交错时的处理方式，例如受保护快照、双缓冲的所有权转换或队列。仅有一个就绪标志，并不能覆盖任意时刻发生的新写入。

7. Busy-Wait、WaitEvent 与多核调度

等待可以采用不同实现。Extended Task 在适当条件下使用 WaitEvent，会进入 Waiting 状态，操作系统可以调度其他 Ready Task；忙等待的执行者则持续检查共享状态，占用相应的 CPU 执行时间。

7.1 两种等待方式的进度条件

机制等待中的执行者对同核调度的影响更适合的场景
Spinlock 忙等待反复尝试获取锁可能持续占用 CPU，取决于锁方法和抢占配置极短且可控的跨核临界区
Barrier 忙等待反复检查参与者到达状态依赖所有参与者的调度进度核启动阶段或有保证的同步点
WaitEventExtended Task 进入 Waiting允许调度其它就绪执行者任务间事件等待
队列/消息等待按具体协议进入等待或主动轮询依赖通信与调度设计数据和通知一同管理

在同一个 Core 上，若高优先级任务自旋等待某个尚未运行的低优先级任务到达 Barrier，而高优先级任务又长期阻止低优先级任务获得 CPU，系统便可能形成进度死锁。设计需要分析参与者所在 Core、任务优先级、抢占方式及实际等待机制。

AUTOSAR OS 对持有 Spinlock 时使用 WaitEvent 等服务还设置了限制，原因之一就是任务可能被取消调度，从而无法释放已持有的 Spinlock。该类约束需要与调用上下文一起审查。

7.2 从正确性设计到响应时间预算

实时系统中的同步不仅要求最终结果正确，还要求等待具有可接受的最坏情况上限。

例如，同步设计可以依次确定：

  • 临界区最长占用时间，包括可能发生的抢占。
  • 等待锁的任务可能遇到的最大竞争次数及优先级关系。
  • Barrier 最慢参与者的初始化或阶段计算时间。
  • 缺席或失败时的退出策略。
  • 对 ISR 响应、任务 deadline 和 Watchdog 监督路径的影响。

这类分析应与 OS 优先级、Spinlock Lock Method 和 Timing Protection 配置结合进行。

8. 两个工程设计案例

下面把同步协议落成两份可操作的设计记录：一份面向共享数据快照，一份面向多核初始化会合。重点是让参与者、同步范围、时间预算和错误处理都能从配置中检查。

8.1 Core0 与 Core1 共享状态快照

假设 Core0 的 Task_Sample_10ms 负责采样，Core1 的 Task_Consumer_20ms 负责计算。两核共用一块包含 SampleFrame 的共享 RAM。

正确性目标： Core1 一次读取的 sequence、timestamp_ms、sensor_value、quality 必须属于同一帧。若业务不允许跨帧混用，所有字段的读取和写入都要纳入一致的同步协议。

实施时建议按下面的顺序审查：

步骤配置或代码位置应得到的结果
1. 找变量定义、MemMap、Linker 段确认 g_frame 位于两核可访问的共享区域
2. 找执行者Task、Runnable 调度及 OS Application 归属明确 Core0 写、Core1 读及调用周期
3. 找同步对象Spinlock 配置和两侧 API确认读写均使用 Spinlock_Frame
4. 看完整临界区GetSpinlock 到 ReleaseSpinlock不在复制中途释放锁，不持锁等待业务事件
5. 看失败路径OS 返回值与调用方锁失败时不继续访问共享数据
6. 看性能锁等待与持有时间的记录点区分数据复制耗时与等待耗时

同样的数据需求，也可以评估 IOC。当通信具备明确的生产者、消费者和队列语义时，使用生成的 IOC 发送/接收接口可能更便于管理数据生命周期；若共享结构很大、复制开销敏感，再评估双缓冲或其它一致性发布方案。具体取舍要依据负载和最坏情况时延。

8.2 三核初始化后统一开放服务

考虑三个阶段任务：Core0 初始化通信服务，Core1 加载标定参数，Core2 准备控制数据。后续业务需要这三部分都就绪。

一种易于审查的方案是为每个参与者明确初始化完成位置，并在此处加入共同的会合协议。假设 Core0、Core1、Core2 分别在第 2、5、8 ms 到达 Barrier，放行点由最慢的 Core2 决定。

参与者到达时间（示例）会合前做什么本轮等待
Core02 ms初始化通信资源约 6 ms
Core15 ms装载标定与默认参数约 3 ms
Core28 ms初始化控制状态约 0 ms

准备实施时，需要把以下条件落实到设计中：

  1. 参与者集合固定且清楚，不能出现代码里有四个调用位置、配置却只声明三个参与者的情况。
  2. 到达位置确定。每位参与者只在本轮完成初始化后报告到达，不能在真正初始化完成前提前到达。
  3. 跨核数据发布有正确内存可见性保证。同步点放行，不应让消费者拿到仍不可见的初始化数据。
  4. 调度进度得到保证。若一个高优先级 Task 一直自旋，而另一个低优先级参与 Task 无法在本核运行，会合可能永远无法完成。
  5. 异常恢复有明确责任。缺席者是否允许退出、启动超时由谁监督、Wdg 是否能够运行，都要结合启动策略决定。

若这只是启动过程的一次同步，一次性 Barrier 就可能满足需求；若 10 ms 周期控制每轮都要会合，则应使用支持轮次切换的同步协议，并重新评估忙等待对 CPU 负载与 deadline 的影响。

9. 验证方法：从访问矩阵到运行时间线

代码和配置能够解释一个同步方案的意图，也能排查相当多的静态错误。运行时分析则进一步验证真实竞争、等待与调度延迟。

分析阶段主要工作典型结果
访问关系列出共享对象、每核读写点与同步原语访问矩阵与冲突候选
静态调用追踪 OS/RTE API、锁定范围和任务上下文关键调用链、可达性边界
构建关联核实源码、生成配置、ELF/Map 和目标固件明确所测的构建版本
运行观测记录 Lock Wait/Hold、到达时间和任务切换实际同步时序与等待分布
异常场景在授权开发环境中验证异常和恢复机制Timeout、错误路径及恢复记录

多核调试要注意观测干预：单独暂停一个 Core，可能让其他参与者在 Barrier 中等待；在锁内设置阻塞断点，也可能人为放大锁持有时间。需要依据调试器提供的同步停机及 Trace 能力选取方案。

10. 结语

原子操作为同步协议提供底层操作能力；Spinlock 以互斥规则保护临界区；Barrier 组织多个参与者的阶段会合；Memory Barrier 参与保证内存访问顺序；Event 则通过操作系统调度表达任务等待。

设计多核系统时，先定义共享对象与同步条件，再判断应该让谁等待、等待期间 CPU 如何执行、状态何时可见、失败后如何恢复。这样选出的机制才可能同时满足正确性与实时性。

如果还需要建立 OS 对象归属与保护模型，可以先阅读 OS Application：对象归属、访问控制与内存保护。关于数据发布与事件状态的典型边界，另见 COM Deferred EventCache 的跨核一致性。
