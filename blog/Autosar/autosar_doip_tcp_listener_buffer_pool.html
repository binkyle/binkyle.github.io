AUTOSAR DoIP TCP 监听建立全链路：Socket 缓冲池、精确匹配与诊断验证

Bin2026/10/30嵌入式系统与 AUTOSARAUTOSARDoIPSoAdTcpIpTCPBuffer Pool大约 12 分钟

在一次 AUTOSAR Classic 以太网诊断联调中，ECU 能够响应 DoIP 的 UDP 发现请求，诊断仪却无法通过 TCP 13400 建立会话。网络抓包中，诊断仪发出 SYN，ECU 返回 RST/ACK。单看这一组报文，很容易把注意力集中在端口、防火墙或者 TCP 状态机上。

真正决定这条连接能否建立的条件，发生在 SYN 到来之前：SoAd 申请到了 TcpIp Socket，但在配置该 Socket 的接收缓冲区时失败，因而没有走到 Bind 和 Listen。

这篇文章沿着这条实际调用链，介绍 AUTOSAR DoIP 的协议分层、SoAd 的监听建立过程，以及一种固定规格 TCP Buffer Pool 的分配设计。文中涉及的配置数值和结构图均为匿名化原理示例，不是原工程的 ECUC 导出或抓包重放。函数名用于定位机制，代码为重新编写的概念示例，不是供应商源码。

1. 从 UDP 发现到 TCP 诊断，是两条不同的路径

DoIP（Diagnostics over Internet Protocol）将车载诊断承载到 IP 网络上。一次典型的测试可以分为三个阶段：

诊断仪                          ECU / AUTOSAR Classic
   │                                  │
   │  UDP：车辆发现 / 车辆识别         │
   ├─────────────────────────────────>│
   │<─────────────────────────────────┤
   │                                  │
   │  TCP SYN → SYN/ACK → ACK         │
   ├─────────────────────────────────>│
   │<─────────────────────────────────┤
   │                                  │
   │  DoIP Routing Activation         │
   ├─────────────────────────────────>│
   │<─────────────────────────────────┤
   │                                  │
   │  UDS 10 01 → 50 01              │
   ├─────────────────────────────────>│
   │<─────────────────────────────────┤

在 AUTOSAR Classic 的典型部署中，TcpIp 负责底层 Socket 与 TCP/IP 处理，SoAd 管理 Socket Connection 和 PDU 路由；DoIP 管理车辆识别、路由激活与诊断消息，诊断负载再经相关路由进入 Dcm。具体的 PduR 接入方式取决于工程配置。

UDP 发现成功只能证明相应 UDP 通路可工作，不等于 TCP Server 已经处于监听状态。 同理，DHCP 成功获取 IPv4 地址也只是 Listener 建立的必要环境条件之一。

这次联调早期确实遇到过 IPv4 Controller 尚未进入可用状态的问题。恢复网络初始化后，UDP 服务已经可用，但 TCP SYN 仍触发 RST/ACK。两个现象发生在同一轮排查中，却属于不同层次，不宜合并为一个原因。

2. SoCon Open 不等于 TCP Listen

SoAd 不是在收到 SYN 时才临时创建监听端口。对需要自动或请求式打开的 TCP Server SoCon，它会在相应状态处理路径中准备监听资源。

这里有三个检查点：

第一，Open 请求与实际打开之间可能存在调度延迟。 SoCon 状态变化由任务或事件处理推动；仅看到 Open 请求计数变化，不能断定 Listener 已经存在。

第二，GetSocket 只是取得一个 TcpIp Socket 资源。 它成功后，仍然可能因为参数设置、Bind 或 Listen 失败而关闭该资源。这次调试中，GetSocket 返回成功，但随后 TcpChangeParameter 返回失败；Bind 和 Listen 因此前置条件不满足而没有执行。

第三，不同模块的索引不能混看。 SoConId 是配置中的连接标识，SoConIdx 是 SoAd 内部数组索引；SoAd 自己的 SocketTcpIdx 与 TcpIp 的 SocketTcpDyn 索引也属于不同的表。定位时应先核对各自的映射关系，不能仅凭数值相同认定是同一个对象。

从 TCP 的角度看，Listener 和接入后形成的连接也不是一个概念。Listener 负责接受连接请求；已经建立的连接则具有独立的对端状态与资源管理。两者的实际 Buffer 占用方式需要看协议栈实现，不能仅按 SoConGroup 数量直接推算。

3. 固定 Buffer Pool：一块连续内存，多个 Descriptor

本案例所涉及的 TcpIp 实现采用构建时配置容量、运行时分配归属的方式管理 TCP RX/TX 缓冲区。

数据内存可以是一块连续数组，描述符则通过起始和结束索引描述每个预配置片段：

Tcp RX Byte Array
┌──────────────┬────────────────────────┬────────────────┐
│ Descriptor 0 │      Descriptor 1      │ Descriptor 2   │
└──────────────┴────────────────────────┴────────────────┘
^              ^                        ^                ^
Start[0]     End[0]                   End[1]           End[2]
             =Start[1]                =Start[2]

Descriptor：{ StartIdx, EndIdx }
Socket：保存已分配 Descriptor 的索引
Descriptor 动态字段：保存当前 Socket 属主

每段的范围通常采用左闭右开区间 [StartIdx, EndIdx)，因此：

BufferLength = EndIdx - StartIdx

这样只需保存边界，不必为每个 Descriptor 重复保存 Length。它也便于在生成阶段核对各段是否重叠、是否超出底层数组边界。

例如，下面这些值完全是教学示例：

DescriptorStartIdxEndIdx长度
A040964 KiB
B4096122888 KiB
C12288204808 KiB

这里的三个 Descriptor 对应三段预留内存，不是三次 malloc()。真正发生在运行时的，是将其中一个空闲 Descriptor 与某个 Socket 关联起来。

3.1 空闲状态如何表示

在这类生成代码里，SocketTcpDyn 可以保存“已分配的 RX Descriptor 索引”；反向的 Descriptor 动态字段保存“占用它的 Socket 索引”。

当索引值等于对应数组的 Size 时，可被用作无效/未分配哨兵值。例如有效索引是 0..N-1，那么 N 不可能表示合法元素，恰好能表示“当前没有分配对象”。

这种双向关联让释放过程有明确的复位点：Socket 清除自己的 Descriptor 引用，Descriptor 也清除属主，并复位与缓冲读写相关的运行时状态。

3.2 分配算法为什么会失败

该版本的 RX 分配逻辑具有三个门槛：

  1. 当前 Socket 尚未持有 RX Buffer；
  2. TCP Socket 处于允许分配的状态（RX 路径要求 CLOSED）；
  3. Buffer 必须空闲，且长度与请求值完全相等。

下面是概念化的算法示意，不是任何商业协议栈的原始代码：

/* 原理示意：固定规格池中的精确匹配 */
bool assign_buffer(Socket *socket, size_t requested)
{
    if (socket->buffer != INVALID || socket->state != CLOSED) {
        return false;
    }

    lock_pool();
    for (size_t i = 0; i < descriptor_count; ++i) {
        if (pool[i].owner == INVALID &&
            pool[i].length == requested) {
            pool[i].owner = socket->index;
            socket->buffer = i;
            unlock_pool();
            return true;
        }
    }
    unlock_pool();
    return false;
}

决定性条件是：

buffer_length == requested_size

如果 Socket 请求 12 KiB，而池中只有上述 4 KiB、8 KiB、8 KiB 三段，结果必然失败。即便三段都空闲、总容量达到 20 KiB，也无法拼成一个 12 KiB 的 Descriptor。反过来，池中存在更大的段也不意味着允许自动降级或向上取整；分配策略由比较条件决定。

精确匹配的优点是资源规格明确、分配过程可预测，能够避开运行时任意尺寸堆分配。但相应代价是配置必须一致：上层请求的每一种大小，都要在下层池中预置对应规格及足够的并发数量。

3.3 跨核锁保护的是什么

资源扫描、选定和属主写入位于跨核临界区中，目的是避免多个执行上下文把同一空闲 Descriptor 同时分给不同 Socket。

跨核互斥可以保护分配的原子性，却不能弥补规格缺失。一个不存在的尺寸，不会因为加锁而出现。这也是排查时要区分“资源配置不匹配”和“资源被占满”的原因。

4. 配置一致性：业务上限必须落到实际资源上

诊断请求容量、诊断响应容量、SoAd Buffer 要求和 TcpIp Buffer Pool 并不是同一项配置。

在这次分析涉及的工程中，沿配置关系可以看到：

DoIP 最大请求容量 ────────┐
                          ├─→ SoAd TCP RX Buffer 请求
Dcm / DoIP 响应容量 ──────┘
                               │
                               ▼
                     TcpIp RX/TX Buffer Pool
                     规格 + 数量 + 内存预算

实际的 RX、TX 配置分别追溯；上图是依赖关系示意，不表示生成工具必然自动传递这些数值。

原来的配置在业务模块和 SoAd 侧要求了某种大缓冲规格，而 TcpIp 的预分配池只提供了较小的规格。RX 分配在精确比较处无法匹配，返回失败；TX 池也缺少对应的大小。这个静态配置事实与运行时的首次 RX 参数设置失败相吻合。

值得注意的是，最初只关注诊断链路，进一步汇总所有 SoConGroup 后，还发现其他服务请求的一个中等规格也不在池内。由此可见，资源池应当按照所有 TCP 使用者的需求整体校验，而不能只补当前报错的一个 Socket。

配置审查可以用下面的矩阵完成：

层次需要核对的对象常见误区
DoIP / Dcm请求、响应与目标缓冲上限把业务最大报文长度直接等同于底层可分配容量
SoAd每个 TCP SoConGroup 的 RX/TX 请求规格只检查正在调试的那一个组
TcpIpRX/TX Descriptor 的精确规格只看总池容量，不看单项大小
TcpIp每种规格的 Descriptor 数量数量等于配置组数，忽略并发连接
Linker / RAM新增静态内存及放置区域编译通过就视为内存裕度充足

从设计角度看，可以把它转成两类可检查约束：规格存在性（请求值能否命中池中的某一规格）和并发容量（同规格可同时借出的 Descriptor 是否够用）。前者可以完全通过 ECUC/生成数组做静态核查；后者还需要结合连接模型、最大并发数和运行时测试。

5. 一次从源代码到报文的定位过程

这次调试之所以能收敛，是因为每一步都沿实际返回值向前追踪，而不是看到 RST 后直接猜测原因。

在调试器中查看这类代码，最好区分已执行的分支和源码箭头当前所在行。内联 Getter、编译优化和调试信息映射可能让箭头位置不够直观；真正可靠的证据是参数值、分支执行结果与函数返回值的组合。

这条链路也说明了一个容易忽略的事实：TCP 参数设置失败可以发生在 Bind/Listen 之前。 当时继续向 Dcm 或 UDS 服务端寻找超时原因，已经偏离故障发生的层次。

6. 配置修复与通信验证

修复采用配置层补齐资源规格的方式：在 TcpIp 的 Socket Buffer 列表中增加所需 RX/TX 规格及相应数量，保留原有业务使用的规格；随后重新生成和编译。没有修改固定池分配算法，也没有强行将失败返回值改为成功。

修复前修复后
SoAd 请求的部分规格在 TcpIp 池中不存在TcpIp 配置增加对应规格
RX 参数设置阶段停止TCP 监听建立具备必要资源条件
TCP 握手失败抓包观察到完整三次握手
DoIP 诊断会话无法建立Routing Activation 与 UDS 会话控制成功

修改后的抓包验证了TCP SYN → SYN/ACK → ACK，随后出现 DoIP Routing Activation Request 和成功的 Routing Activation Response；诊断请求 10 01 收到肯定响应 50 01，其他已允许的会话切换也返回对应肯定响应。

这组证据跨过了三个不同的边界：

  • TCP 握手成功：说明监听与连接建立通路已工作；
  • Routing Activation 成功：说明 DoIP 层允许该诊断连接进入后续路由；
  • UDS 肯定响应：说明诊断请求确实进入诊断服务处理路径并返回结果。

抓包中还观察到 DHCP 地址重新协商以及某次 TCP 连接被 RST 终止，随后又成功重连。仅凭时间先后不能认定 DHCP 事件直接造成 RST；长期稳定性、多客户端并发和资源回收仍需独立验证。

7. 将一次故障转化成配置检查方法

对采用固定 Buffer Pool 的协议栈，设计检查可以前移到生成配置审查阶段：

  1. 汇总需求：按 TCP SoConGroup 收集 RX/TX 请求尺寸，不遗漏不常用的诊断或升级服务。
  2. 核对规格：从生成 Descriptor 的 EndIdx - StartIdx 计算每一项长度，找出不存在精确匹配规格的请求。
  3. 核对数量：建立每种规格与最多并发 Socket 的映射，包含 Listener、已接受连接和关闭释放时序；不能按组数机械推算。
  4. 核对内存：计算新增静态字节数组、描述符和其他管理数据，再使用实际 MAP/链接布局检查 RAM 裕度。
  5. 分层验收：先确认 Socket 参数、Bind/Listen 和 TCP 握手，再验证 DoIP Routing Activation，最后验证 UDS 请求与响应。

从失败的那个 E_NOT_OK 往回看，问题不在 TCP 算法是否足够复杂，而在两个模块之间缺少一条被持续检查的配置契约：上层声明的资源需求，必须能被下层实际提供的资源规格满足。

这条原则不限于 DoIP。静态内存池、PDU Buffer、事件队列和其他预配置资源，都需要同时回答三个问题：需要多大、同时需要几个、资源在什么条件下归还。

阅读边界：本文讨论的是一次特定 AUTOSAR Classic 协议栈实现中的固定缓冲池策略，并非声称所有 AUTOSAR TcpIp 实现都采用相同的精确等值算法。代码与数值示例已抽象化；通信验证描述来自实际联调抓包，未公开内部配置和设备数据。
