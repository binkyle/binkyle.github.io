机器人系统软件与具身智能

Bin2026/10/21机器人系统软件与具身智能机器人系统ROS2软件架构大约 7 分钟

让机器人抬起一只手，看起来只是执行了一个动作。但对软件系统来说，它可能经过任务规划、消息传输、回调执行、关节控制、驱动通信和位置反馈。每一段都可能影响动作是否及时、准确，以及出现异常时能否停在预期状态。

这就是本专栏的起点：关注机器人怎样把一个决定变成可执行、可观测、可验证的动作。 从熟悉的 C++、嵌入式实时系统和通信问题出发，逐步走进 Linux、ROS2、控制框架和具身智能系统。文章不把每一种技术当成孤立知识点，而是放回具体的运行路径中讨论。

读者不需要先掌握运动控制或深度学习。初次接触机器人软件，可以先阅读技术能力地图；如果已经熟悉 ROS2，可以直接查看控制指令的执行链路。

一条控制指令在系统中经历什么

设想一台在仿真环境中的双关节机械臂。任务层要求它把末端移动到某个位置。这里不急着讨论复杂的轨迹算法，先看软件需要共同完成的事情：

任务 / 感知                  看见什么？想完成什么？
    │
    ▼
规划 / 动作生成              目标位置、关节目标或轨迹
    │
    ▼
ROS2 通信与执行器            Topic / Action → DDS → Executor 回调
    │
    ▼
运行时与控制接口             数据是否过期？状态是否允许执行？
    │
    ▼
控制器 / 硬件抽象            读取关节状态 → 计算输出 → 写入命令
    │
    ▼
仿真模型或驱动               产生运动及位置 / 速度 / 力矩反馈
    │
    └─────────────── 状态反馈到控制、规划和任务层

这是一张职责图，并不是要求所有机器人都按相同顺序部署进程。某些机器人把高频控制留在独立实时控制器中，ROS2 只承担任务目标、状态或较低频率的控制指令传递。把所有节点都放进一个 ROS2 Executor，也不会自然得到确定的实时性。

真正需要回答的四个问题

问题涉及的机制工程上如何验证
消息能否送达？Topic、DDS 发现、QoS 相容性、网络/进程边界从发送端和接收端记录序号、配置与拓扑
消息何时被处理？Executor、Callback Group、线程调度、回调负载记录到达事件与回调执行时刻，构造忙碌回调
旧命令能否继续执行？时间戳、有效期、最新状态、控制授权注入过期或乱序命令，观察拒绝和状态变化
动作是否符合预期？控制器、关节接口、硬件/仿真模型及反馈对照命令、实际关节状态与误差，不只看可视动画

这四个问题对应不同层次。消息“可靠送达”，不代表回调立即执行；回调执行，也不代表输出命令仍然有效；关节动起来，也不能证明控制系统已满足安全与实时要求。

把 ROS2、Linux 和控制框架放在各自的位置

ROS2 / DDS：让组件交换有语义的数据

ROS2 负责节点、消息接口与执行框架；DDS 是常见的底层通信中间件方案。Topic 适合连续数据，Service 适合有界请求与响应，Action 适合持续一段时间、需要反馈和取消的目标任务。究竟使用哪一种接口，要由业务语义决定，不能简单按“实时/非实时”分类。

QoS 决定历史缓存、可靠性、持久性等策略，还要关注发布端与订阅端的相容性。传感器状态可能更看重新鲜度，配置类消息可能强调可靠取得；但Reliable 不是低延时保证，Best Effort 也不等于不值得信任。实际选择取决于采样周期、丢失容忍度和应用的恢复逻辑。

Executor / Linux：消息到了，也得有人运行回调

Executor 的职责是选择已经就绪的回调并执行。回调可能来自订阅、定时器、Service 或 Action。单线程 Executor 中，长回调会推迟后续处理；换成多线程也不意味着所有回调都并发，Callback Group 的互斥约束仍然有效。

Linux 线程调度、CPU 负载、锁竞争、内存分配及系统中断共同影响实际时间。分析性能时，至少要分清发送周期、订阅回调间隔和控制器更新/反馈周期，避免用一个“延时”替代所有环节。

ros2_control：把控制器与硬件接口连接起来

ros2_control 提供控制器管理和硬件抽象机制。以常见 Controller Manager 模型为例，控制循环的关键工作是读取硬件状态、执行控制器更新、写出控制命令。硬件组件的生命周期、状态接口和命令接口需要和驱动或仿真模型对应。

它并不规定感知模型应该如何训练，也不保证任意 ROS2 节点满足硬实时。真正能否达到目标周期，还取决于控制器工作负载、线程策略、驱动和所用平台。
