关键结论： Stack Painting 通过填充图案的变化观察历史栈需求；同一 epoch 保留已观察峰值。它不等于当前 SP 深度，也不能单独证明没有溢出。

  • 复现入口： 从第 8 节命令与公开验证记录核对环境、单位、扫描工作量和已知限制；再与CPU 时间模型分别建立预算。

CPU Load 的统计口径

关键结论： 在同一核、同一窗口和同一时钟口径内，将物理时间分配给 Task、Idle、ISR 与已识别的 Kernel gap，再计算 (Total − Idle) / Total。嵌套 ISR 用 exclusive 时间汇总物理开销，避免重复计数。

核心问题： 事件已经出队，为什么 Rx Buffer 的数据仍没有被处理？

  • 关键结论： 在本文的 Put → Copy → SetLength 模型中，消费者可以先取走事件、再读到尚未置位的 Pending。NonCached 与本核关中断都不能把这组操作自动变成跨核事务。

  • 验证入口： 先核对实际 SchM 展开、生产/消费顺序与 Buffer 所有权，再按第 11 节清单检查满队列、Group 状态与补偿路径。

多核嵌入式开发里有一种容易产生误判的现象：共享变量放在 NonCached RAM，读写都是简单赋值，两边也都进入了 SchM Exclusive Area，但事件队列和业务状态仍可能不一致。

这里不需要先假设硬件缓存出错。更值得追问的是：

“事件已发布”与“事件对应的数据已就绪”，是不是同一个不可分割的状态转换？

本文以 AUTOSAR Classic COM 的一种 Deferred Rx + EventCache 实现为例，借助一个可构造的双核交错，讨论缓存可见性、原子性、内存顺序与跨核互斥之间的区别，以及事件驱动系统该怎样维护状态不变量。

文中的代码是根据实际函数关系抽象的示意性伪代码，不是 AUTOSAR 对所有 COM 实现的统一规定。具体项目还应遵循所使用组件的多核部署和并发访问约束。

从库交付到最终镜像

关键结论： Compile 产生可重定位 Object，Archive 组织库成员，Link 完成符号解析、重定位与内存放置。拿到 .a 不代表已经得到可运行程序，也不能用库文件大小直接推算最终 Flash 增量。

  • 适用范围： 本文围绕 TC397 + TASKING 的概念与集成契约展开。实际命令参数、ABI、库变体与 LSL 约束必须对应所用工具链版本。
  • 验证方法： 沿着 Object、归档成员、未解析符号与最终 ELF/Map 逐层核对；代码与命令用于解释机制，不能代替目标工程的链接与运行验证。
  • 相关问题： 编译与放置契约明确后，可继续阅读运行时测量接入，区分“链接成功”与“运行观测有效”。

  • 作为 Consumer：拿到供应商提供的 .a，再链接进自己的 ECU 工程。
